# CONTEXT — curfew domain language

The domain glossary for `curfew`. Agents and skills use THIS vocabulary when naming modules, tests, and discussing the system. Architectural rationale lives in `docs/adr/` (decisions); product framing lives in `work/specs/`.

## What curfew is

Parental control for OpenWrt on a GL.iNet Flint 2 (GL-MT6000): per-child internet schedules, daily time budgets, per-profile website blocking and temporary access tickets, enforced with nftables and AdGuard Home, plus an installer that deploys it to the router over SSH. Guest access is designed but not built.

It is moving from a set of shell scripts to a single Go tool that owns schedules, state and an HTTP UI. The tool absorbs the scripts rather than sitting beside them, and that is now settled: **every operation is a subcommand**, including AdGuard setup, config pull and push, `panic-off`, and installing the tool onto the router from a laptop (`docs/adr/0007-the-tool-owns-every-operation-including-recovery-and-deployment.md`). The one exception is deliberately narrow: a minimal shell escape hatch survives that restores CONNECTIVITY but not policy, so there is always a way back that does not depend on the tool running. It is not a duplicate of the `panic-off` command, which owns the real operation and clears persisted state the hatch knows nothing about.

## Core domain terms

- **profile** — a named family member or device group (`eli`, `tia`, `family`) owning a daily budget and a set of devices. The unit everything else acts on: blocks, tickets, budgets and website rules are all per-profile.
- **device** — one named MAC address. A child typically has several (phone, laptop wired, laptop wireless), and they are blocked and released together as a profile. Per `docs/adr/0003-devices-are-named-and-profiles-group-them.md` a device is becoming a first-class named entity in its own registry, so that a device can be allowed on the network without belonging to any profile. Today, devices exist only as bare MACs inside a profile and their names survive only as comments.
- **device registry** — the intended home for device names and MAC addresses, separate from the grouping of devices into profiles. Not yet implemented; it is the config-schema half of ADR 0003.
- **ungoverned device** — a registered device belonging to no profile: allowed on the network with full access, subject only to network-wide policy such as AdGuard filtering. The printer and the cameras are this in intent, and are currently faked as one-device profiles carrying a meaningless budget.
- **MAC allowlist** — the set of MACs permitted to reach the internet at all. Unknown devices are dropped, which is what stops a child bypassing control by randomising their MAC. Currently derived from profile membership; becomes derived from the device registry under ADR 0003.
- **ticket** — a time-limited grant of internet access to a whole profile, issued from a phone. It overrides a `schedule` or `budget` block while it lasts, and is itself outranked by a `manual` block (`docs/adr/0006-a-block-carries-a-set-of-reasons-and-manual-outranks-a-ticket.md`). It is an override that LAPSES rather than a mutation: on expiry the profile falls back to whatever reasons are live at that moment, with no bookkeeping. Blocking cancels any live ticket, so a later unblock cannot resurrect one. The page that issues it is password-gated, because it is served by the router and is therefore reachable by the very device being blocked. IMPLEMENTED in the Go tool: an element in `ticket_macs` carrying a kernel timeout, granted by tapping a duration on the home page, with the remaining time read back off the kernel rather than tracked in parallel. Two properties are worth knowing before changing anything here. A whole-table reconcile READS BACK live tickets and re-emits them with the time they have LEFT, so a tick can neither drop a ticket nor restart its clock. And `GrantTicket` REFUSES while a manual block is in force, rather than issuing a ticket the chain will ignore: that keeps the ADR's unblock-then-ticket gesture meaningful and closes the hole where a ticket issued under a block springs to life the moment the block is lifted. The legacy shell version (state-file edit plus a background `sleep`) survives only under `legacy/`.
- **guest pass** — a time-limited grant to a device that is **not in the device registry** (not on the MAC allowlist), obtained by a visitor entering a passphrase. NOT YET IMPLEMENTED. The discriminator is registration, not profile membership: an ungoverned device is registered and permanently allowed, whereas a guest is unregistered and allowed only for the pass's duration. Note the privilege inversion this creates: in the enforcement chain a guest pass is matched ABOVE the `schedule`/`budget` block set while ordinary allowlisted devices are matched below it, so for the duration of the pass a guest outranks a registered device that is blocked for those reasons. That is deliberate (a visitor should not inherit a child's bedtime) and it is also the mechanism behind a bypass the guest design has to defend against. It does NOT outrank a `manual` block, which sits above the guest accept (`docs/adr/0006-...`).
- **time budget** — a daily allowance shared across all of a profile's devices. A budget minute counts **actual use above a traffic threshold**, decided in `docs/adr/0001-budget-counts-actual-use-gated-by-a-threshold.md`; the mechanism and the continuity model are decided in `docs/adr/0009-the-budget-continuity-model.md`. IMPLEMENTED. Four optional per-profile values, none of them meaning unlimited: **global budget** (total per day), **continuous budget** (per unbroken session), **continuity gap threshold** (the inactivity that ends a session) and **continuity reset gap** (the wait after exhausting the continuous budget). The last three are a group: all or none. Two further values are GLOBAL rather than per profile: the **daily reset time** (default 03:00, because children are awake at midnight) and the **activity threshold**. The `budget` reason is derived from the usage counters on every check and joins `blocked_macs`, the same set the schedule uses, so it needs no new tier and a ticket overrides it by chain position. The legacy shell `budget-check` incremented unconditionally every minute from midnight, so `eli|240` meant "blocked at 04:00" whether or not a device was switched on; that is a bug, not a definition, and it survives only under `legacy/`.
- **session (continuity)** — an unbroken stretch of use. It ends two ways and only one of them costs anything: **naturally**, when inactivity reaches the gap threshold, which is free and refills the continuous allowance in full; and **punitively**, when the continuous allowance is exhausted, which costs the reset gap. The reset gap is WALL-CLOCK, not inactivity, because the profile is blocked throughout and no traffic survives enforcement to be observed. Full rationale, including why a reset gap shorter than the gap threshold is refused at load, is in ADR 0009.
- **activity threshold** — how many bytes of UPSTREAM traffic in a minute count as actually using the internet. Global, because it is a property of how devices behave rather than of a child. **Its default (50 KiB/min) is an unvalidated guess and is labelled as one everywhere it appears**, including a warning at daemon startup: ADR 0001 requires it to be calibrated against real idle household devices and that cannot be done in a container. The home page reports each profile's observed bytes per interval, for every profile including unbudgeted ones, precisely so a household can replace the guess with a measurement.
- **accounting table** — `curfew_accounting`, a SECOND nftables table holding counter rules only, hooked at `filter` priority 0 while enforcement sits at -10. Separate from the `curfew` table because `ApplyDesired` replaces that table whole on every drift and would zero any counter in it (measured). The priority split is what makes accounting count only traffic that SURVIVED enforcement, so a blocked device's retries cannot burn its own allowance (measured: exactly 0 bytes, for both the schedule and the manual drop tiers). It counts LAN-to-WAN by source MAC only; the download direction cannot be attributed to a device at that hook at all (measured: 0 bytes by `ether daddr` against 1,066,928 for the same rule without the MAC match).
- **block rule** — a reusable named list of domains (`no_streaming`, `no_gaming`) defined once and applied to any profile, resolved to IPs and enforced as nftables sets.
- **website blocking** — applying a block rule to a profile for a period, distinct from blocking the internet outright.
- **schedule** — the recurring times a profile is blocked or has a block rule applied, expressed as **windows** carrying a day-of-week selector, so a profile can have several a day (22:00 to 08:00 and 12:00 to 13:00) and differ between school nights and weekends. It lives in its own tool-owned config file (`docs/adr/0008-configuration-is-tool-owned-structured-files-split-by-concern.md`), and it is evaluated as DESIRED STATE by a reconcile loop rather than fired as cron edges. That is what makes a missed moment self-healing: a router that boots at 22:05 is blocked within a tick, where a missed cron edge was lost for the night. Today it is still crontab lines, which cannot be rendered in a UI, cannot express a window, and silently change meaning when mistyped (see `work/notes/findings/busybox-crond-treats-a-bad-time-field-as-a-wildcard.md`).
- **block reason** — why a profile is blocked: `schedule`, `budget` or `manual`. A block carries a **SET** of concurrent reasons and lifts only when the set empties; each operation adds or removes exactly the reason it owns, which is what stops a daily budget reset clearing a bedtime block and lets a UI say why a child is offline. Decided in `docs/adr/0006-a-block-carries-a-set-of-reasons-and-manual-outranks-a-ticket.md`. `schedule` and `budget` are FACTS the system computes; `manual` is a DECISION it stores, so they are distinguishable by construction rather than by inferring who ran a command. IMPLEMENTED for all three, and the set is expressed by the CHAIN rather than by a stored list: `manual` puts a MAC in `manual_blocked_macs` while `schedule` and `budget` put it in `blocked_macs`, so removing one reason cannot remove the other. The daily budget reset is structurally incapable of clearing bedtime, because it can only zero budget counters and cannot see a manual block or a window at all.
- **persisted block state** — the state that must survive a reboot, stored outside tmpfs so a reboot does not silently grant internet. **The authoritative list of its members is the `blockstate.State` type in `internal/blockstate`, and this glossary deliberately does not repeat it.** That rule comes from the enforcement spec, where three successive drafts each dropped a different member while retyping the list in prose; the list now lives in the one place that cannot drift from what is actually written to disk, and ADR 0009 records the move. In outline only: a parent's DECISION plus the budget's counters, at `/etc/config/curfew/state.json`, keyed by PROFILE NAME rather than MAC so a device added to a blocked profile is blocked too. The `budget` and `schedule` reasons are deliberately absent, because both are recomputed on every check: budget from its counters, schedule from the clock. There is no separate restore step: desired state is recomputed from the files on every reconcile, so the boot path and the steady state are the same code, and there is no restore path that can rot from disuse. Distinct from tickets and guest passes, which are kernel timeout sets and are MEANT to die with the router.
- **enforcement vs state** — the distinction this project keeps getting wrong (rationale: `docs/adr/0004-tests-assert-on-the-packet-path.md`). **Enforcement** is what nftables will actually do to a packet; **state** is what the state files and logs claim. When they disagree the firewall is right, so status must be derived from the firewall.
- **packet path** — whether a real packet from a given source MAC actually reaches the internet. The only trustworthy assertion about enforcement, and the thing the test suite historically never checked. Now checked by `test/test_helper/netns.bash`; rationale in `docs/adr/0004-tests-assert-on-the-packet-path.md`.
- **`curfew` table** — the dedicated `inet` nftables table holding the sets and the forward chain, hooked at priority -10 so it runs ahead of fw4 without mixing into it. The MAC sets are `manual_blocked_macs`, `ticket_macs`, `guest_macs`, `blocked_macs` and `allowed_macs`, matched in that order; the order IS the policy and is fixed by `docs/adr/0006-...`. In the Go tool that order is DATA, `contract.Tiers`, walked by `internal/enforce` to build the chain and by `internal/httpui` to decide what a device's state actually is, so the page and the ruleset cannot disagree about what outranks what. `guest_macs` is the one member not yet present: guest passes are not built, and an accept rule for a set nothing populates would sit unexercised in the middle of the chain, so the tier is added when the feature is.
- **home page vs settings page** — the UI is split by WHEN a surface is needed, not by what it acts on. The **home page** answers "is this child online, and can I give them twenty minutes?": one row per profile, state read from the firewall, budget remaining, a block/unblock button, preset ticket durations and a custom-minutes box. The **settings page** (`/settings`) owns everything that CONFIGURES the household: schedules, profile membership, per-profile budgets, and the global budget settings. Configuration is a sit-down job done rarely, so keeping it off the home page keeps the common case the easy one. Settings edits redirect back to settings and confirm they saved; home actions redirect home, where the badge changing is its own confirmation.
- **enforcement floor vs policy layer** — the split this project is being built along. The **floor** is the nftables contract: which sets exist, the order they match in, what survives a reboot, what fails loudly, and who may ask for a ticket. The **policy layer** decides what SHOULD be true: schedules as windows, budget accounting, and the status page. The floor is identical whichever language owns it, which is why it is settled and packet-proven independently of the port.
- **work/ contract** — the on-disk system this repo uses, defined by the reference docs in **`work/protocol/`** (copied here by `setup`): `WORK-CONTRACT.md` (the contract), `CLAIM-PROTOCOL.md`, `REVIEW-PROTOCOL.md`, `TASKING-PROTOCOL.md`, `SURFACE-PROTOCOL.md`, `task-template.md`, `spec-template.md`, `ADR-FORMAT.md`. Three REGIME umbrellas — `notes/` (capture buckets), `tasks/` (the build board), `specs/` (the spec lifecycle) — plus top-level `questions/` and `protocol/`. One markdown file per item, status = the folder it lives in (never a field). Capture buckets: `notes/ideas/` (proposed), `notes/observations/` (spotted, unverified, append-only), `notes/findings/` (verified external/domain ground truth, each with a `source:`). ADRs (`docs/adr/`, format in `work/protocol/ADR-FORMAT.md`) record what WE decided and why.
- **promptGuidance** — the per-repo NUDGE namespace in `dorfl.json` whose members (currently just `testFirst`) strengthen the wording in the worker's in-band prompt. NOT a gate: the `verify` step is still the only acceptance bar. Omitted ⇒ off; absence is the default.

The dorfl version is PINNED via `dorflCmd` in `dorfl.json` (`npx dorfl@0.11.2`), so bare `dorfl` self-forwards to a fixed version instead of floating with whatever is globally installed. To bump: edit `dorflCmd`, then `dorfl sync`. This repo has no JS manifest, so the pin deliberately uses `npx` rather than introducing a `package.json`.

The `verify` gate runs the test suite inside a container built on a real `openwrt/rootfs` image, with `NET_ADMIN`, `SYS_ADMIN` and `NET_RAW` and `net.ipv4.ip_forward=1`, and with no mocked system tools. `SYS_ADMIN` is what allows `ip netns add`, which the packet-path harness needs; the sysctl is defensive, since a container namespace inherits the host's forwarding setting. podman and docker are interchangeable here, and note that `podman compose` may delegate to the docker-compose plugin and therefore to the docker daemon, so a green gate does not by itself prove podman was exercised.

Any topology failure in the harness (a dead server, a missing route, forwarding off) makes every probe read unreachable, which is indistinguishable from a perfectly blocking firewall. That is why the harness asserts a **baseline** before it asserts anything is blocked.
