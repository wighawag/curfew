# The budget continuity model, and where accounting lives

**Status:** accepted

`docs/adr/0001-budget-counts-actual-use-gated-by-a-threshold.md` settled what a budget minute MEANS and deliberately left the mechanism open. This records the mechanism, and the edges of the continuity model, which is new and which nobody had written down. It answers, in one place: where the counters live, what they count, when a session ends, what exhausting one costs, and when the day starts again. None of it is re-litigating ADR 0001 or ADR 0006; a budget block remains a MAC in `blocked_macs`, the same set the schedule uses, so no new tier is added to `contract.Tiers`.

## Accounting lives in its own table, and counts upstream only

**Accounting is a separate nftables table, `curfew_accounting`, hooked at `filter` priority 0 while enforcement sits at -10.** It contains counter rules and nothing else: no rule carries a verdict and the chain policy is accept, so it is structurally incapable of influencing what happens to a packet.

The separate table is forced by measurement, not preference. `internal/enforce.ApplyDesired` deletes and recreates the whole enforcement table on every apply, and an apply happens on every drift: every schedule boundary, every device edit, every block. Measured on the packet-path harness: a named counter created inside the `curfew` table read `{bytes:4242}` before an apply and was **gone** afterwards, with zero objects present, while the identical counter in a separate table read `{bytes:1234}` both before and after, and kept counting across three further rebuilds. A counter in the enforcement table would therefore have been silently zeroed several times a night, and the budget would have been quietly wrong rather than visibly broken. Carrying counters across the rebuild the way live tickets are carried was the alternative; a separate table is chosen because it needs no carry-over step that a future change can forget, and because it is what ADR 0001's hook-priority split already pointed at.

The priority split delivers the property ADR 0001 requires. Measured, baseline first: with an allowed device the counter moved 850 bytes for one page fetch; with the same device schedule-blocked its retries moved the counter from `{bytes:850}` to `{bytes:850}`, and with it manually blocked, likewise. **A blocked profile burns no budget, structurally**, because the packet is dropped at -10 and never reaches the counter at 0. That covers the manual tier as well as the schedule tier, and it is why it needs no special case anywhere in the policy layer.

**Accounting counts LAN-to-WAN traffic only, matched by source MAC, mirroring the enforcement match exactly.** The download direction is not counted because it cannot be attributed to a device at all at this hook, which was measured rather than assumed: a 1 MiB download moved a WAN-to-LAN counter matching the client's `ether daddr` by **0 bytes**, while the identical rule with no MAC match moved by **1,066,928 bytes**. The control is what makes that conclusive; the LAN-side link-layer header does not exist yet at the forward hook, so there is no device MAC to match on. Attribution by IP address does work (measured: the same 1,066,928 bytes) and is rejected: it needs a MAC-to-IP mapping this system does not have, it breaks when a DHCP lease changes, and it would decouple accounting from the identity enforcement acts on.

The consequence is that **the threshold is calibrated against upstream bytes**, which is a different number by roughly two orders of magnitude from an intuition about megabytes downloaded. Measured on the harness: a 1 MiB download produces 14,169 upstream bytes, a ratio of 1.35%; one small page fetch produces 850; an idle client produces exactly 0.

## The threshold default is a guess, and is labelled as one

`budget.DefaultActivityThreshold` is 50 KiB per minute of upstream traffic. **It is not calibrated.** ADR 0001 requires calibration against real idle household devices and that cannot be done in a container, which has no idle household devices in it. What is measured is only the scale: at the 1.35% ratio above, 50 KiB/min is roughly 3.7 MB/min of download, about 500 kbps sustained, which sits below SD video and above music-only streaming, and far above a phone sending keepalives. Both ends of that reasoning extrapolate from one topology.

So the number ships as a starting point with three mitigations: it is configurable (`budget_settings.activity_threshold_bytes_per_minute`), it is expressed as a RATE so it keeps its meaning if the accounting interval changes, and the home page reports each profile's **observed** bytes per interval, including for profiles that carry no budget, so a household can watch its own idle devices for an evening and replace the guess with a measurement. Accounting therefore runs for every profile with devices, not only budgeted ones, which is what makes that calibration path exist.

A limitation to state rather than hide: a byte threshold distinguishes "this device is essentially silent" from "this device is moving data". It cannot distinguish a child watching video from a phone in a pocket uploading a photo library. No choice of direction fixes that, and ADR 0001 already accepts it by choosing a threshold at all.

## A session ends two ways, and only one of them costs anything

- **Naturally**, when inactivity reaches the **gap threshold**. The session ends at no cost and the next use starts a fresh one with the continuous allowance **full**.
- **Punitively**, when the **continuous allowance** is exhausted. The profile is blocked and must wait out the **reset gap**.

Only the punitive end costs a reset gap. The alternative reading was checked rather than assumed, and it is incoherent: if stopping voluntarily also cost a reset gap, then a child who put their phone down for the gap threshold would be penalised for it, the gap threshold would become a trap instead of a rest, and there would be no way to end a session cheaply at all, which is the thing the gap threshold exists to express.

**The reset gap is WALL-CLOCK from the moment of blocking, not inactivity.** This is not a preference; inactivity is unobservable here by construction. During the cooldown the profile is blocked, so no traffic survives enforcement, so the accounting counter cannot move (measured above: exactly 0 bytes). An inactivity-based cooldown would therefore observe unbroken inactivity always, making it identical to wall-clock, unless it counted traffic that enforcement had already dropped, which ADR 0001 forbids precisely because a blocked device's retries must not burn the allowance. Wall-clock is the only coherent answer and it is also the only implementable one.

**After the reset gap the continuous allowance refills FULLY.** A partial refill needs a refill rate nobody specified, and it creates a ratchet in which the fifth session of a day is shorter than the first for no reason a child can predict or a parent can explain. The daily budget is what limits the total; the continuous budget limits the stretch; keeping the two knobs orthogonal is what makes "4 hours a day but only 2 at a stretch" mean what it says. Note also that a natural session end must refill fully or the gap threshold means nothing, so a partial refill would make being cut off worse in two ways when it is already worse in one.

**A reset gap shorter than the gap threshold is REFUSED at load.** It inverts the incentive: waiting out the penalty would be cheaper than stopping voluntarily, so the optimal play becomes "always burn to exhaustion" and the gap threshold punishes only the child who moderates themselves. A configuration that quietly means the opposite of what was written is the exact failure recorded in `work/notes/findings/busybox-crond-treats-a-bad-time-field-as-a-wildcard.md`, and the response there was the same: refuse it at the door rather than reinterpret it.

Two further validations follow the same rule. **`continuous`, `gap` and `reset_gap` are a group: all three or none**, because each is inert or perverse without the others (a continuous allowance with no gap can never end a session by stopping; with no reset gap it costs nothing to exhaust; a gap or reset gap with no continuous allowance does nothing at all). And **`continuous` may not exceed `daily`**, because the continuous allowance could then never be reached. ADR 0003 already names a budget field that cannot mean anything as the smell that motivated splitting devices from profiles; these refusals stop that shape recurring.

## The day, the ticket, and what the reset clears

**The reset time is GLOBAL, not per profile**, defaulting to 03:00. The requester specified it as configurable with that default and did not say which. Global is chosen because the reset time is the boundary of "a day", and two children under one roof disagreeing about which day it is would make a shared family profile incoherent and would turn the day marker from one value into a per-profile one. Nothing found in the request or the code argues the other way. It is recorded because it is a choice, and it is cheaply reversible: move the field into the profile and treat the global one as the default.

**It is DERIVED, never fired.** The question asked is "which budget day are we in right now?", answered from the clock exactly as `internal/schedule` asks whether a window contains now. Nothing is ever scheduled at 03:00. That is what makes a daemon which was down across the reset time still see the new day, and it is what makes a reset time pointed at an hour that does not exist on a spring-forward day roll over exactly once, at the jump, rather than being missed for a night.

One guard on top: **the rollover only ever moves forward**, and it has TWO halves, because during implementation only having one was measured to defeat it entirely. Refusing to move the day MARKER backwards protects the counters from being zeroed; but the accounting path also READS the counters under a day key, and reading them under an earlier day returns zero state, so the very next write would overwrite a spent allowance with a fresh one. Both the reads and the writes therefore go through a single `EffectiveDay`, which is what makes the rule impossible to apply on one path and forget on the other. An OpenWrt router has no RTC and boots at the epoch, and a backwards rollover would hand every child a fresh allowance on every power cut, which is the reboot-grants-internet defect this system exists to remove. The cost, stated: a clock wrongly set into the future freezes the rollover until real time catches up. That is the rarer fault and it errs towards staying blocked.

**The daily reset clears ALL budget-owned state: usage, the in-flight session, and any live cooldown.** All three belong to the day that has just ended, and leaving a cooldown standing would mean a child blocked at 03:05 for a reason belonging to a day that no longer exists, which is the class of stale reason ADR 0006's reason set exists to prevent. It is not a free pass either: the whole daily allowance returns at the same instant, so a surviving cooldown would be a rounding error against it. And per ADR 0006 the reset removes only the reason it owns; it cannot see a manual block or a window, so unlike the implementation it replaces it is structurally incapable of clearing bedtime.

**A ticket burns both the global and the continuous allowance, and does not cut short a cooldown.** Both fall out of having no bookkeeping rather than being separate rules. Accounting continues during a ticket because the traffic survives enforcement, so global usage accrues; the session tracker is driven by that same observed activity, so a session accrues too, and making it not would mean teaching the tracker what a ticket is. The cooldown is wall-clock and runs regardless: a ticket overrides the budget block by chain position while it lasts, and when it lapses, if the cooldown is still running, the block reapplies on the next tick with nothing to remember. A profile ticketed while in cooldown keeps its session pinned at exhausted, so the ticket cannot be used to launder a fresh session.

## Consequences

- The persisted state list grows, and it MOVES. The enforcement spec required that list be stated in exactly one place and never restated loosely in prose, because three drafts each dropped a different member. That one place is now the `blockstate.State` type, which cannot drift from what is actually written to disk; the spec is a launch snapshot that is explicitly not maintained, and `CONTEXT.md` and the spec now point at the type instead of copying it. The members are the manual reason, the budget-day marker, and per profile the usage, the session, the last-activity marker and the cooldown deadline.
- The previous counter reading is deliberately NOT persisted. It baselines a kernel counter that dies with the table, so keeping it would preserve a number whose meaning had already gone. It lives in memory, and the cost is one skipped interval after a restart, in the child's favour.
- A counter is a cumulative total, so a reset makes it go backwards. Two defences, not one: the accountant reports a generation that changes whenever it rebuilt the table, so a reset we caused is KNOWN; and a reading lower than the last one is skipped anyway, so a reset somebody else caused (a manual `nft flush`, a reboot) is caught too. A skipped interval neither credits nor charges.
- The accounting table must not be rebuilt on every tick or usage would never accumulate while every individual read still looked plausible. The shape is therefore compared and written only when the household actually changed.
- The documented escape hatch, `nft delete table inet curfew`, remains complete on its own. The accounting table carries no verdict, so leaving it behind cannot block anything; measured on the packet path, a client reaches the internet with the enforcement table deleted and the accounting table still present.
