`.acceptance/dnspolicy.test` reported `FAIL` on one full `docker/acceptance.sh` run, with no test name captured because the run was piped through `grep ... | head`, which truncates and can SIGPIPE the script. It did not reproduce: seven subsequent runs of the binary on its own and two subsequent full suite runs all exited 0.

Written down because an acceptance failure that is explained away is how a gate rots. Two candidate causes, neither confirmed:

- The rig's known soft spot. `lookupVerdict` retries a UDP query six times and returns `ERROR:` rather than a verdict when every attempt times out, which `mustResolve` and `mustBlock` then fail. The test comments already call this out: a timeout is neither blocked nor resolved, and on a loopback-heavy container it happens.
- Cross-binary interference. `acceptance.sh` runs all eight test binaries in one container, and `deploy.test` also starts a real AdGuard; `startAdGuard` does `killall AdGuardHome` and waits for a real DNS answer, but nothing waits for the previous AdGuard's port 53 to be released. Simulating that order (accounting, daemon, deploy, then dnspolicy) passed once.

If it returns, capture the run with the output going to a file rather than a pipe, so the failing test name and its diagnostic survive.

**Update, later the same day: the second cause is real and was reproduced deliberately.** Adding an acceptance binary for `internal/adguard` broke two `deploy.test` cases, because the new one wrote a stand-in `/etc/init.d/adguardhome` that implemented only `start` and `stop` and exited 0 on anything else. A later binary drove `restart` through the adoption path, got a silent no-op, and failed with "its config was changed but the running server has not picked it up", a message that describes a fault the earlier test caused. The fix was to implement every verb and to restore the file in cleanup, but the general hazard stands: these binaries share one container, one `/opt/AdGuardHome`, one port 53 and one `/etc/init.d`, so any fixture left behind is charged to whichever test runs next, and the failure surfaces far from its cause.

**Update, 2026-11-18: seen again, this time with the name.** While gating `serialise-dhcp-commits-with-one-lock`, `.acceptance/dnspolicy.test` failed twice in three runs with `--- FAIL: TestACurfewListLeftDisabledInAdGuardIsSwitchedBackOn` at `dnspath_test.go:765: baseline: the exception applies: opensea.io from fd00:c0ff:ee::a1 should RESOLVE, got BLOCKED` (the FIRST assertion, before the test disables anything). Neither failure reproduced afterwards: four runs of that test alone on HEAD (e8a8cb3) and on the working tree, three full binary runs of each, and one full run of the remaining binaries were all green, with identical timings (60s per full binary run) for HEAD and the change. The change under test only adds a lock around the DHCP transaction, which runs before the AdGuard half of the Tick, and that half was untouched. So the likeliest reading is a timing window on the baseline itself: the Tick publishes curfew's list through a disable/enable re-fetch, and the test queries straight after, so a slow AdGuard engine rebuild on a loaded host would answer with the old engine. Not confirmed; if it returns, the next step is to log AdGuard's filter-rebuild lines around that assertion.

**Update, later on 2026-11-18: cause found and fixed in the harness.** It got more frequent once the local-DNS-names tests joined the binary (two failures in three full runs; still one in four with them skipped, so it predates them). A temporary dump on failure showed AdGuard's state was already correct (the `curfew-eli` client had its IPv6 ids, curfew's list was enabled with its rules), and a query repeated from the same address every 250ms for five seconds got the CORRECT verdict every time, starting with the first one after the failing assertion. So the failing query was simply sent before AdGuard had applied the change: AdGuard applies a client or list change asynchronously after the API call returns, and the harness asserted synchronously. `mustResolve` / `mustBlock` (and the three direct "should now be BLOCKED" checks) now assert that the verdict APPEARS within 3s, still from the child's own address; five full runs of the binary afterwards were all green. A first hypothesis (an AdGuard still shutting down overwriting the next test's config) was tested and did not change the rate, so it was reverted. This observation can be deleted once the gate has stayed green for a while.
